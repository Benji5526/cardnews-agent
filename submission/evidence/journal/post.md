카드뉴스 앱에 이미지 작업자를 붙이면서 배운 것을 정리한다. 핵심은 두 가지다. 429는 인증 문제가 아니라 한도 문제라는 것, 그리고 성공은 응답 문장이 아니라 저장된 파일로 판단한다는 것이다.

## 오늘 배운 것

학습 메모 항목은 총 3개다.

1. `agy -p`는 헤드리스라 도구 권한을 대화형으로 받을 수 없어서, 응답에는 "생성했다"고 나와도 파일이 안 생길 수 있었다. `--dangerously-skip-permissions`를 주면 파일이 생겼고, 그래서 성공은 저장된 파일이 실제 이미지로 열리는지로 판단한다.
2. Gemini API가 HTTP 429를 돌려주면 키 인증이 틀렸다는 뜻이라고 생각해서 키부터 다시 만들었다. (이 이해는 틀렸다. 아래 "내 메모에서 바로잡은 점" 참고)
3. 키 오류와 한도 오류는 같은 재시도로 풀리지 않아서, 첫 실패에서 남은 카드를 건너뛰고 멈추게 했다.

## 핵심 개념

### 429는 속도·한도 문제다

- 429 Too Many Requests는 클라이언트가 일정 시간 안에 너무 많은 요청을 보냈다는 4xx 응답이다. 요청 속도를 늦추라는 신호이며, 명세는 RFC 6585 section 4다.
- 429 응답에는 `Retry-After` 헤더가 포함될 수 있다. 값은 초 단위 숫자이거나 HTTP 날짜 형식이다. 예: `Retry-After: 3600`(60분 후 재시도). 헤더가 없으면 지수 백오프 등으로 간격을 늘리라고 안내한다.
- Gemini API 공식 가이드는 429 `RESOURCE_EXHAUSTED`를 일시적이라 재시도할 수 있는 오류로 분류한다. 해결책은 지수 백오프(약 1초에서 시작해 2초, 4초, 8초), 지터, 최대 재시도 횟수 제한이다.
- 잘못되었거나 권한 없는 API 키 문제는 429가 아니라 403이다. 400, 402, 403은 재시도해도 해결되지 않는 오류로 분류된다.

### Gemini API 한도의 단위

- 한도는 RPM(분당 요청), TPM(분당 입력 토큰), RPD(일일 요청)로 평가된다. 하나라도 넘으면 다른 한도에 여유가 있어도 오류가 난다. 모델에 따라 이미지 생성용 IPM이나 일일 토큰 한도(TPD)가 추가될 수 있다.
- 한도는 API 키 단위가 아니라 프로젝트 단위다. 문서 원문은 "Rate limits are applied per project, not per API key."이다. 그래서 같은 프로젝트에서 키를 새로 만들어도 한도는 풀리지 않는다. RPD는 태평양 시간 자정에 초기화된다.
- 유료 티어에는 10분 롤링 윈도우의 지출 기반 한도(Tier 1 $10, Tier 2 $50, Tier 3 $200)가 있고, 넘으면 429 `RESOURCE_EXHAUSTED`가 반환된다. 무료 티어에는 적용되지 않는다.

### 헤드리스 `agy -p`와 권한

- 서드파티 가이드(Hexdocs, v0.1.0, 비공식으로 보임)에는 `agy -p "..." --dangerously-skip-permissions` 예시가 있다. 대화형 확인이 불가능한 환경에서는 파일·명령 동작이 사용자 승인을 기다릴 수 있다고 설명하고, 통제된 환경에서 이 플래그를 쓰라고 권한다. 다만 검색 결과 요약으로만 확인했고 페이지를 직접 열어 보지는 않았다.
- 이 플래그는 이름 그대로 위험하다. 모든 권한 확인을 건너뛰므로 작업 폴더가 격리된 통제 환경에서만 쓰는 편이 안전하다. (이 위험성 자체는 공식 문서로 확인하지 못했다.)
- 별개의 문제로, `agy -p`는 stdout이 실제 터미널이 아니면 출력이 비거나 멈출 수 있다. `agy-headless-bridge` 패키지는 pty(의사 터미널)로 감싸 실행해 이 문제를 우회한다. GitHub 이슈도 서브프로세스, 파이프, 백그라운드 작업 같은 비-TTY 환경에서 print 모드가 무한정 멈춘다고 보고한다. 권한 문제와 원인이 다를 수 있으니 구분해서 봐야 한다.
- 헤드리스나 CI 환경에서는 서드파티 치트시트가 소개하는 방법으로, settings.json에서 provider를 gemini로 지정하고 `GEMINI_API_KEY`를 환경 변수로 export할 수 있다.
- agy(Antigravity CLI) 저장소는 2026-05-13에 공개됐고, 개인 계정에서는 2026년 6월에 호스팅형 Gemini CLI를 대체했다고 한다. 이 시점은 서드파티 출처 기준이며 공식 문서로 교차 확인하지 못했다.

## 예시

성공 여부를 응답 문장이 아니라 저장된 파일로 판단하는 흐름이다. 아래는 내 설계 판단을 옮긴 의사 코드이며, 공식 문서에서 가져온 코드가 아니다.

```text
for card in cards:
    run agy -p "<이미지 요청>" --dangerously-skip-permissions   # 격리된 작업 폴더에서만
    if 저장된 파일이 실제 이미지로 열리지 않음:
        실패로 기록하고 남은 카드는 건너뛴 채 중단
```

- 응답에 "생성했다"고 적혀 있어도 파일을 열어 보기 전에는 성공이 아니다.
- 첫 실패에서 멈추는 것은 키 오류나 일일 한도 소진처럼 재시도로 풀리지 않는 경우를 위한 선택이다. 공식 가이드는 429를 일시적이라 백오프 재시도 대상으로 보므로, 429에서 바로 멈추는 것은 공식 권장과 다르다. 일시적 한도라면 `Retry-After`나 지수 백오프로 재시도하는 편이 권장 방식이다.

## 내 메모에서 바로잡은 점

- **"429면 API 키 인증 오류"는 틀렸다.** MDN과 Gemini 공식 문서 모두 429를 속도·한도 문제로 보고, 키 문제는 403으로 구분한다. 키를 새로 만든 것은 불필요했을 가능성이 크다.
- 한도가 프로젝트 단위이므로, 같은 프로젝트에서 새 키를 만들어도 효과가 없었을 것이다.
- 내가 실제로 받은 429의 구체적 원인(분당 한도, 일일 할당량, 이미지 생성 한도, 지출 한도)은 확인하지 못했다. 오류 본문의 reason 필드를 봐야 알 수 있다. 사용량이 낮은데도 429가 난다는 포럼 보고가 있지만 원인이 확정된 것은 아니라 단정하지 않는다.
- "응답에는 생성했다고 나오는데 파일이 안 생겼다"는 현상이 권한 대기 때문이라는 설명은 서드파티 가이드와 맞지만 공식 확인은 아니다.
- "저장된 파일이 실제 이미지로 열리는지 검증한다"는 원칙은 원문이 뒷받침하는 내용이 아니라 내 설계 판단이다.
