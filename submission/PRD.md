# PRD — 학습일지 → 블로그 포스트 + 요약 카드

카드뉴스 워크플로(주제 → 조사 → 후보 선택 → 심층 검증 → 편집 판단 → 스토리보드 승인 → 이미지·글자 → 검수·부분 수정 → 내려받기)를 내가 자주 하는 작업에 맞게 바꾼 PRD다. 카드뉴스 모드는 그대로 두고, 첫 화면에서 "학습일지" 모드를 고르면 아래 흐름으로 동작한다.

> 이 PRD는 튜토리얼 키트의 PRD.md를 받지 못한 상태에서, 안내문의 요구사항과 실제 구현·실행 결과를 바탕으로 작성했다.

## 1. 해결할 불편

공부한 내용을 블로그에 정리할 때마다 (1) 내 메모가 원문과 맞는지 다시 확인하지 않고 쓰게 되고, (2) 틀린 이해가 글에 그대로 남고, (3) 글과 요약 이미지를 따로 만드는 데 시간이 든다.

## 2. 기대 산출물 (확인 가능한 결과)

한 번 실행하면 다음이 ZIP으로 나온다.

| 파일 | 내용 | 확인 방법 |
|---|---|---|
| `post.md` | Jekyll front matter가 있는 학습일지 포스트. "내 메모에서 바로잡은 점" 섹션 포함 | 파일을 열어 원문 링크·메모와 대조 |
| `cards/card-NN.png` | 1080×1350 요약 카드(3~8장). 글자는 이미지와 별도 레이어로 배치 | PNG를 열어 글자 잘림·내용 확인 |
| `sources.json`, `sources.md` | 확인한 사실, 근거 링크, 확인일 | 링크를 열어 대조 |
| `image_usage.json` | 이미지 작업자·도구·크기·"설명용 생성 이미지" 기록 | 파일 확인 |

자동 게시는 하지 않는다. 사람이 검수한 파일을 직접 사용한다.

## 3. 카드뉴스 PRD에서 가져온 것 / 바꾼 것

| 구분 | 그대로 가져온 것 | 바꾼 것 |
|---|---|---|
| 흐름 | 후보 비교 → 선택 → 검증 → 편집 판단 → 스토리보드 승인 → 제작 → 검수 → 내려받기, 질문 대기, 실패·재시도, 새로고침·재시작 복구 | 입력과 조사 방식, 산출물에 포스트 추가 |
| 편집 규칙 | 형식 두 가지 비교·추천, 후킹은 확인된 사실만, 이미 입력한 조건은 다시 묻지 않기 | 형식 후보를 TIL형·튜토리얼형·Q&A형·개념 설명형으로 교체 |
| 제작 | 별도 호출 후킹 설계, 글자 별도 레이어, 이미지 작업자 분리, 파일 검증 | 카드 수 3~8장, 포스트 작성 단계 추가 |
| 날짜 | 기준일 표시 | 게시일 대신 "확인일" (메모에는 원문 게시일 개념이 없음) |
| 조사 기간 | — | 쓰지 않음 (최근 N일 검색이 아니라 내 메모에서 시작) |

## 4. 설계

| 설계할 부분 | 내용 |
|---|---|
| **입력** | 주제 한 줄, 학습 메모(20자 이상), 참고 링크(선택), 편집 방향(선택). 결과를 만드는 데 필요한 것만 받는다. |
| **AI 판단** | (1) 메모에서 개념 후보 4~7개 추출, 링크·공식 문서를 읽어 메모와 대조 (2) 메모가 원문과 다르거나 불확실한 부분을 "⚠ 확인 필요"로 표시 (3) 글을 쓰기에 부족한 점을 `gaps`로 표시 (4) 글 형식 두 가지를 장단점과 함께 비교·추천 (5) 첫 카드 후킹 후보 2개를 근거·과장 위험과 함께 비교해 선정. 모든 판단의 근거는 화면과 `sources.json`에서 확인할 수 있다. |
| **사람 결정** | 다룰 개념 1~3개, 독자 수준, 글 형식, 제목·표지 방향, 카드 수. 편집 방향에 이미 적은 항목은 다시 묻지 않는다. 스토리보드 승인, 카드별 수정 요청, 최종 승인. 메모가 부족하면 보완 여부. |
| **도구 행동** | 웹 검색·원문 읽기(Claude CLI), 이미지 생성(agy 또는 Gemini), 포스트 작성, 카드 PNG 렌더, ZIP 저장. 외부 게시·전송은 없다. 이미지 작업자는 빈 작업 폴더에서만 실행하며, agy의 도구 자동 승인은 `AGY_ALLOW_ALL_TOOLS=1`로 명시적으로 켠 경우에만 쓴다. |
| **검수와 산출물** | AI 사실·출처 검수(카드 vs 확인된 사실), 글자 넘침 측정, 내보낸 파일 점검(수량·크기·이미지 파일·출처·기준일, 확인 못한 항목은 "미확인"으로 남기고 사람이 볼 항목을 안내). 카드를 고치면 최종 승인이 풀리고 포스트는 "다시 쓰기"로 맞춘다. |

## 5. 사람이 결정하는 지점 (대기 상태)

`select`(개념 선택) → `editorial`(독자·형식·제목) → `storyboard`(기획 승인) → `review`(수정·최종 승인). 이 단계들은 정상 대기 상태(`waiting_for_user`)이며, 답변 전에는 다음 제작이 시작되지 않는다. 같은 답변을 두 번 제출하거나 지난 질문에 답하면 현재 작업을 바꾸지 않고 거절한다(질문 버전 `qVersion`).

## 6. 자료 부족·실패 처리 규칙

- 메모가 너무 짧거나 모호하면 개념을 지어내지 않는다. 부족한 점(`gaps`)을 화면에 표시하고, 후보를 만들 수 없으면 오류와 함께 "메모 보완하고 다시 정리"로 이어진다.
- 링크가 없는 개념은 출처가 "내 메모"이며 카드에 링크 출처를 넣지 않는다. 공식 문서에서 확인하지 못한 내용은 "확인하지 못한 부분"으로 남긴다.
- 검색·이미지·응답 형식 실패는 원인과 해결 안내를 보여 주고, 확정한 기획과 성공한 카드는 유지한 채 재시도한다. 이미지가 막히면 "대체 배경으로 계속"을 선택할 수 있고, 실제 생성은 미완료로 기록된다.
- 이미지 성공은 응답 문장이 아니라 저장된 파일을 다시 열어 확인한 경우에만 기록한다.

## 7. 수용 기준

1. 메모 한 편으로 개념 후보 → 선택 → 질문 → 스토리보드 → 카드·포스트 → ZIP까지 끝난다.
2. 메모와 원문이 어긋난 곳이 "바로잡은 점"으로 포스트와 카드에 남는다.
3. 편집 방향에 적은 독자·형식은 다시 묻지 않는다.
4. 자료가 부족한 입력에서 그럴듯한 내용으로 채우지 않고, 부족한 점을 보여 주며 메모 보완으로 이어진다.
5. 내보낸 파일 점검에서 확인하지 못한 항목이 통과로 표시되지 않는다.
6. 새로고침·서버 재시작 후에도 단계와 질문이 복원된다.

## 8. 범위 밖 / 미결

- 외부 게시(블로그 커밋·푸시)는 하지 않는다.
- 엔진 교체와 라이선스 스톡(Pexels 등) 이미지는 구현·검증하지 않았다. CC0·퍼블릭 도메인 이미지는 Wikimedia Commons에서 사람이 직접 고르는 방식으로 구현·검증했다. 두 프로젝트 동시 실행은 검증했다(OBSERVATIONS.md 6번).
- agy 도구 자동 승인 대신 필요한 도구만 허용하는 규칙은 문법을 확인하지 못해 적용하지 못했다.
